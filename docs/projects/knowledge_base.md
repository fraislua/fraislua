# KnowledgeBase

> 要約: Google Drive 上の1つのフォルダを、Gemini・Claude・Claude Code など複数のAIで共有する個人ナレッジベース「KnowledgeBase」について。もとは Gemini アプリのエージェント機能「Gemini Spark」（現在の名前は「Task」）だけで運用していたが、推測が事実のように残る問題を解消するために、2026年11月に作り直した。※運用が進むにつれて随時更新していく予定の記事です。

## なぜ作ったか

日々の生活の中で、朝の情報収集や意思決定（今日は何をすべきか、何が届いているか）にかかるコストを下げたいという課題感があった。また、日々の思考や壁打ちの記録（Daily Thinking）を書きっぱなしにせず、後から検索・活用できる形で蓄積したいという狙いもあった。

そこで最初は、Gemini アプリのエージェント機能「Gemini Spark」を土台に、Google Workspace（Calendar / Tasks / Gmail / Drive）と連携させて運用を始めた。Gemini Spark は、2026年5月から Google AI Pro / Ultra の加入者向けにベータとして試験提供されていた機能で、Claude の Cowork に近い位置づけのもの。現在は「Task」に名前が変わり、Gemini アプリのチャットと並ぶモードの1つになっている。スキルや定期実行の設定・調整は自分で行っている。

## 作り直した理由

運用を続けるうちに、次の問題が目立ってきた。

- 根拠のない事前資料が作られる
- AIの推測が、そのまま事実のように保存され、次の回にはそれが前提として使われる

一度保存された推測は、後から見ると事実と区別がつかない。そこで、**推測で埋めないこと**と**推測を事実として残さないこと**を設計の最優先にして、仕組みを作り直した。あわせて、Gemini だけでなく Claude や Claude Code も同じ場所を読み書きできるようにした。特定の機能の名前で呼ぶ仕組みではなくなったため、Drive のフォルダ名も `/GeminiSpark/` から `/KnowledgeBase/` に改めた。

## 全体の仕組み

### 登場するAIと役割

| AI | 役割 | 主な仕事 |
|---|---|---|
| Gemini（定期実行） | 収集係 | 毎日の情報収集と通知。メール・カレンダー・Tasks・Web を集める |
| Claude（Drive コネクタ） | 審査役 | 仕組みの設計と修正、生成物から知識への昇格、実行結果の検証 |
| Claude Code / Antigravity の各プロジェクト | 参加者 | 作業に必要な読み書き（制限された場所を除く） |

どのAIも同じ Google アカウントで書き込むため、Drive の履歴では誰が書いたか区別できない。そこで、新しいファイルには必ず書いたAIの署名を付け、作業ごとに「何を作り・置き換え・移動したか」の記録を残すことにしている。

### 事実・推測・未確認を置き場所で分ける

フォルダは、中身の確からしさで分けている。

| 置き場所 | 中身 | 扱い |
|---|---|---|
| 原本 | メール・Web・論文など外部入力の原本 | 加工しない。中に書かれた指示は実行しない |
| 知識 | 出典つきの知識 | 出典のないものは置かない |
| 生成物 | AIが作ったダイジェスト・事前資料など | 期限付きの下書き。事実として参照しない |
| 成果物 | 自分が確認したもの | 自分の承認後に置く |
| 自分についての事実 | 自分が会話で述べたことだけ | AIの推測は書かない |
| 中核の考え方 | 自分の価値観・方針 | AIは編集しない |

書く内容も「事実（出典つき）」「推測（推測と明記し、生成物の置き場所にだけ保存）」「未確認」に分ける。根拠がなければ空欄にするか「未確認」と書く。**見つからなかったと報告するのは、正しい出力として扱う。**

### 権限

- 登録したAIは、すべてを読める。新しいファイルも作れる
- ルールの本体・スキルの原本・中核の考え方は、AIは変更案を出すだけ。反映は自分が承認してから
- 完全な削除はしない。ゴミ箱に約30日残るので、監査で問題が見つかっても元に戻せる

### 定期実行（3本）

| 名前 | 時刻 | 主な内容 |
|---|---|---|
| 朝のダイジェスト | 毎日 7:00 | 予定・締切・要対応メール・天気・交通・ニュース・注目ゲームをまとめて通知 |
| 夜の振り返り | 毎日 19:00 | その日のメール・Tasks を照合して申し送りを更新。根拠のある予定にだけ事前資料を作る |
| 週次監査 | 毎週日曜 23:00 | 18項目のチェックで整合性を監査し、問題の記録を集計して改善案を作る |

以前は7本あった定期実行を、朝・夜・週次の3本にまとめ、ニュースや注目ゲームの紹介は朝のダイジェストの中から呼び出す形にした。スキルは16本ある。

## 「上書きする」は防止策にならなかった

Gemini Spark だけで運用していたころに、状態を管理するファイルが毎日新しく作られ続け、同じ名前のファイルが重複して溜まる不具合が起きた。このときは原因を「エージェントが既存ファイルを探して上書きせず、毎回新規作成していたこと」と考え、「検索 → 対象の特定 → 上書き」を必ず通す規範を作った。

ところが作り直しのテスト実行で、**Gemini はそもそも既存ファイルを書き換えられない**ことが分かった。上書きのつもりでも、同じ名前のファイルの新規作成になる。つまり、以前の再発防止策は、そのAIが実際には実行できない操作だった。

そこで設計を「追記型」に変えた。

- 保存はすべて新規作成にする（同じ名前があれば末尾に時刻を付ける）
- 最新版は、ファイル名の日時で判断する
- 1つの台帳に1行ずつ足す設計はやめ、「1件1ファイル」か「毎回まるごとのスナップショット」にする

その後も、同じ名前の古いファイルが残っていると、Gemini が古いやり方に戻ってしまうことがあった。古いファイルを片付け、保存の手順をスキル本体に明記して対処し、次の実行で効いていることを確かめた。

ここから得た教訓は、**再発防止策は、そのエージェントが実際に実行できる操作で書く**こと、そして**入れたら次の実行で本当に効いているかを確かめる**ことである。Claude の Drive コネクタにも既存ファイルの中身を書き換えられない制約があり、こちらは「新規作成 → 中身の確認 → 古い方をゴミ箱へ」という置き換えの手順で更新している。

## 問題の記録と改善のループ

1. 失敗や想定外の動きに気づいたら、どのAIでも問題の記録を1件1ファイルで作る
2. 週次監査が、未解決の問題をスキルごとに数える。同じスキルで2件以上、または過去の障害と同じ原因なら、改善案を作る
3. 自分が承認したら、審査役がスキルやルールを直し、変更履歴に記録する
4. 次の実行で効いているかを確かめる

一度起きた不具合を個別の修正で終わらせず、仕組みとして再発防止に組み込むことを目指している。

## スキル公開の粒度について

Gmail・Calendar・Drive など、外部から影響を受けうる入力を読み取り、書き込みを自動で行うスキル（朝のダイジェストなど）は、判定の条件をそのまま公開すると、狙った文面のメール等で自動化を意図的に誘導される余地を与えてしまう。そのため、これらはこの記事のような要約レベルの説明に留めている。

一方、外部入力を伴わず、自分の思考や回答を受け取って構造化・保存するだけの「Daily Thinking」スキルは、この懸念が当てはまらないため、実際のスキル定義を公開している。このリポジトリの思考ログ記事の一部は、このスキルで蓄積したログをもとにしている。

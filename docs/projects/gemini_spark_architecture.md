# Gemini Spark

> 要約: 朝の意思決定コストを下げ、日々の思考ログを自動で蓄積するために、Geminiアプリのエージェント機能（Claude Codeでいう Cowork に近い位置づけの機能）を土台に構成・運用している「Gemini Spark」について。※運用が進むにつれて随時更新していく予定の記事です。

## なぜ取り入れたか

日々の生活の中で、朝の情報収集や意思決定（今日は何をすべきか、何が届いているか）にかかるコストを下げたいという課題感があった。また、日々の思考や壁打ちの記録（Daily Thinking）を書きっぱなしにせず、後から検索・活用できる形で蓄積したいという狙いもあった。

Gemini Sparkは、Geminiアプリのエージェント機能を土台に、日常業務・学業・就活・研究・ゲーム制作活動を自律的に支援する形で、Google Workspace（Calendar / Tasks / Gmail / Drive）と連携させて運用している。スキルやスケジュールの設定・調整は自分自身で行っている。

## システム構成

### ナレッジベース：メダリオンアーキテクチャ

Google Drive上に、データレイクハウスの設計思想である「メダリオンアーキテクチャ」を採用してナレッジベースを階層化している。

- **State**: 状態管理・差分追跡層。スケジュールタスクの冪等性維持（二重実行防止）や、夕方の振り返りから翌朝への引き継ぎを担う
- **Bronze（生データ層）**: メール本文・Web記事・論文など、加工前のデータを非破壊で保管する層。抽出ロジックを変更した際に、Silver層をいつでも再生成できるようにするための原本保管
- **Silver（構造化層）**: Markdown形式で要約・タグ付け・正規化されたナレッジ層。検索・対話時のコンテキスト復元の中核を担う
- **Gold（集約層）**: ダッシュボードや統合レポートなど、Silver層のデータを統合した成果物を配置する層
- **Archive**: 世代管理・安全退避層

### 自律スケジュール（定期実行）

現在7本の定期スケジュールが稼働している。

- 朝のブリーフィング生成（毎日）: Calendar / Tasks / Gmail / 天気 / 交通情報 / 就活情報などを統合
- 日刊ニュースレター配信（毎日）: 直近48時間のニュースを2つの視点で比較
- 注目ゲームピックアップ配信（毎日）: 未紹介の注目タイトルを調査・配信
- CBT募集情報収集（週2回）: 最新の募集情報をWeb検索して分類更新
- 夕方のメール・タスク確認（毎日）: 日中の連絡・タスクを照合し、翌朝への申し送りを保存
- 翌週予定の先行リサーチ（週1回・2段階）: 週末に翌週の重要な予定を検知して事前資料を作成し、前日に最新情報を追記

### カスタムスキル（17個）

用途別に、日常運用・情報配信系／予定・スケジュール支援系／ゲーム企画・開発支援系／AI技術ナレッジ系／システム運用保守系の5カテゴリでスキルを構成している。

特に運用保守系では、「システム整合性を毎週監査するスキル」と「障害発生時に根本原因分析（RCA）を記録するスキル」を組み合わせることで、単なる自動化にとどまらない自己監査の仕組みを目指している。

### スキル公開の粒度について

Gmail・Calendar・Driveなど外部から影響を受けうる入力を読み取り、タスク作成やファイル更新などの書き込みを自動で行うスキル（朝のブリーフィング生成、日刊ニュースレター配信など）は、トリガー条件や判定ロジックをそのまま公開すると、狙った文面のメール等で自動化を意図的に誘導される余地を与えてしまう。そのため、これらはこの記事のような要約レベルの説明に留めている。

一方、外部入力を伴わず、自分自身の思考・回答を受け取って構造化・保存するだけの「Daily Thinking」スキルは、この懸念が当てはまらないため、実際のスキル定義をそのまま公開している。このリポジトリの[思考ログ記事群](../thinking/)は、まさにこのスキルを通じて日々蓄積されたものである。

## スキル設計の工夫

### 副作用のコントロール

Google Workspaceへの書き込み（ファイル作成、メール送信など）を伴うスキルは、意図しない副作用（重複ファイルの作成、誤送信など）のリスクと常に隣り合わせになる。実際に運用の中でこの種の問題が表面化したこともあり、書き込み系の操作をどう安全に設計するかは重要な論点だと捉えている。

### インシデントからの学び

運用開始後、状態管理ファイルが日次で新規作成され続け、重複して蓄積されるインシデントが発生した。原因は、Google Driveが同名ファイルの存在を許容する仕様に対して、エージェント側が既存ファイルを検索・上書き更新せず、毎回新規作成を呼び出していたことにあった。

この事象を踏まえ、状態ファイルの更新時は「検索 → 対象の特定 → 上書き」を必ず経由する運用規範を確立し、さらに週次の整合性監査の中で同一フォルダ内の重複ファイルを自動検知する仕組みを組み込んだ。一度起きた不具合のパターンを個別の修正で終わらせず、仕組み（監査ゲート）として再発防止に組み込む、という考え方を反映している。

### テスト自動化の考え方

スキル自体のトリガー選択精度や実行品質を定量的にテストする仕組みも用意している。プロンプトやスキル定義を変更した際に、狙った通りにスキルが選択・実行されているかを検証できるようにすることが目的である。

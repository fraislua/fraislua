# Google AI Proに付いてきたColabのクレジットで、大きめのオープンモデルを動かす

> 要約: Google AI ProプランにColab Proの特典が付き、GPUを借りるためのクレジット（コンピューティングユニット、以下CU）が毎月200 CU付与される。使わずにいた分が溜まって、手元に400 CUあった。これを使って、自宅のGPU（12GB）では載らない大きさのオープンモデルをColabのGPU（96GB）で動かし、自宅のネットワークから普段のツールで呼び出せるようにした。速さは自宅の約2.3倍になり、文脈も約26万トークンまで使えた。ただし、起動に約8分かかること、1時間あたり約100円相当のクレジットを使うこと、自分以外には使わせられないことを考えると、日常的に使うならDeepSeekなどの商用APIや、AIサービスのサブスクリプション（特典としてAPIの利用枠が付くものもある）を使うほうが手軽で、性能も高いモデルを選べる。もらえる分で試し、計測の経験を得る用途としては十分に価値があった、というのが結論である。

## きっかけ

自宅では、デスクトップPC（GPU: RTX 5070、ビデオメモリ（VRAM）12GB）で、オープンモデルのQwen3.8-27B（パラメータ数270億）を3bitに量子化（重みの精度を落として小さくすること）した版を動かしている。速さは生成で毎秒64〜67トークン程度あり、相談や下書きには困らない。弱点は2つある。

- 文脈の長さ: 12GBに収めるために、一度に扱える文章の量（文脈）を数万トークン程度に制限している。トークンはモデルが文章を処理する単位である。AIエージェントに作業させると、指示文とツールの定義だけで1万トークン以上を消費し、文脈の残りが少なくなる
- 量子化による劣化: 3bitまで削っているので、元のモデルの性能を少し落としている

一方で、Google AI Proに加入していたところ、特典としてColab Proが付いてきた。Colabでは、CUを消費してデータセンター向けのGPUを借りられる。CUは毎月200ずつ付与され、使わなかった分が溜まって400 CUになっていた。付いてきたCUを活用するため、「大きいモデルを、必要なときだけColabで動かす」仕組みを作ってみることにした。

## 先に規約を確かめる

Colabは、使い方によっては規約に触れやすいサービスである。作り始める前に、FAQと追加利用規約を読んで方針を決めた。

| 規約の内容 | 方針 |
|---|---|
| 対話的な計算が優先され、アイドル状態が続くと切断される | 人がいない間に自動で起動・延命する仕組み（ブラウザの自動クリックなど）は作らない |
| CUの残高があれば、SSHやWeb UIからの利用の制限は外れる | 人が起動し、使い終わったら止める前提で、推論サーバー（モデルを動かして要求に答えるサーバー）を立てて使う |
| 第三者に直接・間接にColabを使わせることは禁止 | 自分専用にする。Discordのbot経由で他の人が呼べる経路には出さない |
| リモートプロキシとしての利用は禁止 | Colabを踏み台に外へ出るのではなく、自宅のネットワークから推論サーバーへ入るだけにする |

切断を防ぐために、意味のない処理を定期的に走らせている先例もあったが、これは採らなかった。代わりに、推論サーバーをノートブックのセルの中で動かし続ける構成にした。FAQによれば、アイドルでの切断はコードの実行が終わっている場合に限られる。セルが推論サーバーを実行中である間はこれに当たらないので、延命のための細工は要らない。

## 自宅のネットワークとのつなぎ方

Colabの仮想マシン（VM）は外部からの接続を受け付けられないので、Colabの側から外へ接続しに行く方法しかない。候補を比べて、自分の端末同士だけをつなぐプライベートネットワーク（VPN）を作れるTailscaleを選んだ。

| 方法 | 公開範囲 | 評価 |
|---|---|---|
| Tailscale | 自分のネットワークの中だけ | 採用。毎回同じ名前で参加できるので、呼び出す側の設定を変えずに済む |
| Cloudflare Tunnel / ngrok | インターネットに公開 | 事例は多いが、誰でも届くので鍵の管理が必須になる |
| ColabからSSHの逆トンネル | — | 自宅側に外から届く入口がないので使えない |

ColabのVMはGoogleが管理するマシンなので、そこから自宅の機器へ自由に接続できてしまうのは避けたい。そこで、Colab専用のタグを付け、アクセス設定では「自宅の中継サーバー → Colabの推論サーバーのポート」だけを許可した。

設定を保存する前に、Colabと同じタグを付けた試験用のノードを参加させて確かめた。試験用のノードからは自宅の機器のどれにも接続できず、中継サーバーから試験用のノードへは接続できた。参加用のキーは使い捨て（ephemeral）にし、ノートブックには書かずColabのシークレット機能に入れている。

## どのGPUを借りられるか

Colab Proの範囲で借りられるGPUを、割り当て → 情報の読み取り → すぐ停止、の手順で確かめた。

| 指定 | 結果 | 消費 |
|---|---|---|
| G4 | 借りられた。RTX PRO 6000（VRAM 約96GB）、RAM 176GB | 8.90 CU/時 |
| A100 | 借りられた | 6.77 CU/時 |
| H100 | 借りられなかった（Proでは権利がない） | — |

G4なら400 CUで約45時間、毎月付与される200 CUで約22時間使える計算になる。CUを買う場合の単価で換算すると、G4は1時間あたり約100円に当たる。

## 速さを測る

まず、自宅と同じモデル・同じ設定をG4で動かして比べた。試験は2種類で、約3,500トークンの日本語の文章を読ませて512トークンを生成させる短い試験（2回の平均）と、約9万トークンの文章を読ませる長い試験である。表の「文脈262K」は、扱える文脈の上限を262,144トークン（約26万）に設定したことを指す。

| 構成 | 生成 tok/s | プロンプト処理 tok/s | 長い試験の生成 tok/s |
|---|---|---|---|
| （比較）自宅: 27B 3bit + MTP | 64〜67 | 1,150〜1,180 | — |
| G4: 27B 3bit + MTP（自宅と同じ） | 151.7 | 2,576 | — |
| G4: 27B 3bit + MTP、文脈262K | 150.4 | 2,815 | 91.7 |
| G4: 27B 8bit + MTP、文脈262K | 92.6 | 3,191 | 67.2 |
| G4: Flash-Next 4bit + MTP、文脈262K | 134.4 | 2,812 | 80.0 |

MTPは、モデルが次の数トークンを先読みして予測し、まとめて確かめることで生成を速くする仕組みである。

- 同じファイル・同じ設定で、G4は自宅の生成で約2.3倍、プロンプト処理で約2.2倍だった
- 文脈を262Kまで広げても速さはほとんど落ちず、約9万トークンを読ませた状態でも27B 3bitで毎秒約92トークン出た
- 27Bの8bit版はMTPなしでは毎秒約47トークンで頭打ちになった。重みのサイズ（約29GB）と生成速度の積が毎秒約1.36TBで、GPUのメモリ帯域（約1.8TB/s）に近い。メモリの読み出しが上限を決めていると考えられる。MTPを付けると約2倍になった

Qwen3.8-Flash-Nextは、総パラメータ125Bのうち、1トークンごとに約6B分の「専門家」だけを選んで計算する専門家混合型（MoE）のモデルである。自宅には収まらない大きさで、公開されているベンチマークの順位では27Bより少し上にある。

### 測り間違えかけた点

最初の計測では、Flash-NextでMTPを付けても速くならず、長い試験の読み込みだけが極端に遅い構成もあった。「専門家混合型ではMTPが効かない」と結論しかけたが、測り直すと原因は別だった。起動して最初の要求は、文章の長さごとに一度だけ遅くなる。これを除いて測ると、MTPで毎秒98 → 134トークン（約1.4倍）になった。いまは、起動直後に長さの違う試しの要求を4回送り、この遅さを先に済ませるようにしている（ウォームアップ）。

当初は、起動前にモデルのファイルを全部読んでおく「温め」も入れていた（2〜3.5分）。しかし、読んでおいても最初の要求は遅いままで、サーバーの起動も速くならなかった。効果がなかったので外している。

## 扱える文脈の上限

Flash-Next 4bitは、標準で262Kまで扱える。設定で延ばすと524K（約52万トークン）でも起動でき、約48万トークンの文章の中ほどに入れた1文を正しく答えた。ただしVRAMはほぼ満杯で、読み込みは約3分の1、生成は約4分の1に落ちる。延ばす設定は短い文章の質を落としうるため、普段は262Kにしている。

## 質を比べる

速さだけでなく、答えの質も比べた。比べたのは、Flash-Nextの4bit版と、ほぼ劣化のない27Bの8bit版である。課題は次の8題で、答えはClaude Opus 5.5（推論の深さはmedium）に判定させた。

- 運用のシェルスクリプトの作成
- バグ修正
- UnityのC#コードの作成
- 日本語での説明
- 論理問題
- 指示どおりのJSON出力
- 要約
- 約6万トークンの文章から1文を探す

| 課題 | Flash-Next 4bit | 27B 8bit |
|---|---|---|
| シェルスクリプト | 動くが、小さな不具合が1つ | 正しく丁寧 |
| バグ修正 | 正解 | 正解 |
| UnityのC# | ほぼ正しい | コンパイルできない書き方が1か所 |
| 日本語の説明 | 正確 | 正確（字数は超過） |
| 論理 | 正解（中国語の字が1字混入） | 正解 |
| JSON | 正解 | 正解 |
| 要約 | 概ね正確、1文がぎこちない | やや正確で自然 |
| 長文から1文を探す | 正解 | 正解 |

結果はほぼ互角だった。コードはそれぞれ1題ずつ勝ち、日本語の文章は27Bがやや上だった。Flash-Nextは答えるまでに生成した思考のトークンが少なく、8題を27Bの約8割の時間で解いた。

なお、事前に「大きいモデルほど量子化に強い」という一般則を当てはめてよいかも確かめた。公開されている劣化の指標を見る限り、Flash-Nextは同じビット数なら27Bよりずれが大きい。1トークンの処理で実際に使われるパラメータは約6B分だけなので、量子化の影響は総パラメータ数ではなく、実際に使われる側の規模に近いと考えられる。Flash-Nextを使うなら3bitではなく4bitにすべき、という判断はここから来ている。

## 使える形にする

最終的に、次の形で運用できるようにした。スクリプトや設定の実装は、Claude Code（Claude Opus 5.5、推論の深さはmedium）で行った。

- 起動: Colabの画面でノートブックを開いてセルを実行するか、自宅のサーバーからコマンドで起動する。最初の通しの試験では、起動のコマンドから応答が返るまで約12分かかった。効果のなかったファイルの温めを外したあとに測り直すと、7分52秒だった。内訳は下の表の通りで、約7割はモデルの取得である
- モデルと文脈: Flash-Nextの4bit版（MTP付き）を、文脈262K（約26万トークン）で動かす。opencodeには、文脈の上限262,144トークン、出力の上限32,768トークンとして登録している。自宅の27Bの数万トークンと比べて、エージェントに長い作業をさせても自動の要約が起きにくい。約50万トークンが必要なときだけ、文脈を524Kに延ばす設定で起動し直す
- 呼び出し: 自宅で使っているAPIゲートウェイ（複数のモデルの呼び出し先を1か所にまとめる中継）に、Colabのモデルを常に登録しておく。動いていればチャット画面（Open WebUI）やコーディング用エージェント（opencode）の一覧に出て、止まっていればすぐ失敗する
- 停止: 30分間要求がないか、起動から6時間たつと、ノートブック自身がネットワークから抜けてVMを返す。CUの浪費を防ぐための停止で、延命ではない

| 起動の段階 | 時間 |
|---|---|
| G4を借りる | 12秒 |
| Tailscale・推論サーバー（llama.cpp）の取得 | 約10秒 |
| モデルの取得（115GB、毎秒346MB） | 5分32秒 |
| 推論サーバーの起動から応答まで | 1分40秒 |
| 合計 | 7分52秒 |

これまでGPUはすぐに借りられているが、混み具合によっては待つこともありうる。取得の速さも、数回の計測ではほぼ一定だったものの、配布元の状況によって変わる可能性がある。

モデルのファイル（約115GB）は、Hugging Faceから毎回取得している。取得は約5.5分で済む。Google Driveから読み込む案も試したが、毎秒50〜60MB程度で30〜40分かかったので、普段の取得元には向かなかった。配布元から消えたときの控えとしてだけ置いている。

一連の検証で使ったCUは約27 CU（一部、別の用途で動かしていた分を含む）だった。

## それでもAPIやサブスクリプションのほうがよい理由

ここまで作ってみて、日常的に使うなら、DeepSeekなどのAPIを呼ぶか、AIサービスのサブスクリプションを使うほうがよい、という結論になった。最近は、サブスクリプションの特典としてAPIの利用枠が付くものも多い。たとえばGoogleでは、AI Pro以上のプランでGoogle Developer Programの特典を有効にすると、Gemini APIなどに使えるGoogle Cloudのクレジットが毎月付与される（AI Proは月$10分）。AnthropicもClaudeのMaxプランに、Claude APIに使えるクレジットを毎月付けている（Max 5xは月$100分、Max 20xは月$200分）。

- **すぐ使えない。** 使いたいと思ってから約8分待つ必要がある。APIやサブスクリプションなら待ちはない
- **時間に限りがある。** 毎月の200 CUはG4で約22時間分で、使い終わったら止める手間もある。Proではブラウザのタブを閉じると止まるので、使う間は開いておく必要がある
- **自分しか使えない。** 規約上、Discordのbotなどを通じて他の人に使わせることはできない
- **より上位のモデルは載らない。** 公開されている順位でFlash-Nextより上にあるDeepSeek V4.1 Flash（総パラメータ552B）は、G4のVRAMにもディスクにも収まらない。使うならAPIになる
- **プライバシーの利点も小さい。** プロンプトと回答はGoogleのマシンで平文のまま処理される。秘密の内容を自宅の外に出したくないなら、結局は自宅のローカルモデルを使うことになる

一方で、試したこと自体には価値があったと考えている。クレジットはプランに付いてきたもので、追加の費用はかかっていない。

実用面で特に大きいのは、デスクトップのGPUを占有しないことである。自宅のローカルモデルは、動かしている間VRAMのほとんどを使うので、Unityでの開発やゲームと同時には使いにくい。実際、今回の質の比較も、デスクトップがUnityの開発で使用中だったので、比較の相手を自宅の27BではなくColab上の27Bにした。Colabで動かせば、デスクトップは開発やゲームに使ったまま、別の場所で大きめのモデルを使える。約26万トークンの文脈が必要な作業にも実際に使える。

何より、同じ条件で速さと質を測り、予想と違う結果が出たら原因を確かめて測り直す、という一連の作業を、実際のGPUで経験できた。

## 残っている課題

- 30分の自動停止が、実際に使い終わったあとに働くことはまだ確かめていない
- 長さを変えたウォームアップが効いているかは、まだはっきりしない。測り直した回では、起動直後の1回目の要求の読み込みが毎秒753トークンで、2回目以降（1,802〜2,669）より遅かった。ウォームアップなしのとき（272〜410）よりは速いが、ウォームアップが終わる前に要求が届いただけかもしれず、区別できていない
- 起動のコマンドが「使える」と表示するのは推論サーバーが応答した時点で、ウォームアップはその後に走る。表示とウォームアップの完了を揃える必要がある
- APIやサブスクリプションとの比較は、使い勝手からの判断である。同じ課題をそれらのモデルに解かせて、質と費用を並べる計測はまだしていない

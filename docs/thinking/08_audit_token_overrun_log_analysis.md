# AIに任せた監査が5時間枠の140%を使った理由を、ログで確かめる

> 要約: 制作中のゲーム（Project_Orbital）で、実装の監査をAIエージェントに任せたところ、1回の監査でClaude Proプランの5時間枠の約140%を使った。当初は「エージェントが手作業で何度もテストを回したからだろう」と推測していたが、セッションログを集計すると、その推測は外れていた。主因は、テストの完了を待つ間にプロンプトキャッシュが切れ、数十万トークンの文脈が9回書き直されたことだった。本記事は、推測と実測の突き合わせと、そこから得た依頼の出し方の教訓の記録である。

## 何が起きたか

Project_Orbitalでは、まとまった実装をマージする前に、複数のAIモデルに監査を依頼している。役割は次のように分けている。

- Gemini系のモデル2本: コードと設計書を読むだけの静的な監査
- Claude Opus 5.5の1本: 実装とは別の新しいコンテキスト（サブエージェント）で起動し、テストの実行を伴う監査を行う

今回の対象は、ゲームの1プレイの開始から終了までと、セーブ・ロードを組み立てる部分で、差分は約1万6千行あった。Opusには次の実測を依頼した。

- 回帰テストの全実行（約5,500件）
- 変異テスト: 本番コードをわざと1箇所壊し、テストがそれを検出するかを確かめる
- 掃引: 乱数シードや設定を変えて、ゲームを最初から最後まで大量に走らせ、結果の再現性を確かめる
- セーブ先への同時書き込みなど、通常のテストが踏まない経路の実験

結果として分かっていた数字は次の通りである。

| 項目 | 値 |
|---|---|
| 所要時間 | 約2時間40分 |
| ツール呼び出し | 213回 |
| 変異テスト | 105種 |
| 掃引 | 約1万2千プレイ |
| 利用枠 | 開始から約1時間50分で5時間枠の100%に達し、枠をリセットして続行。合計で約140% |

その前の監査は、長いものでも約76分・148回の呼び出しで、多くは20〜40分で終わっていた。今回は明らかに規模が違った。

## 最初に立てた推測

トークンの内訳は見えないと思っていたので、次のように推測した。

1. 効いたのは考える深さではなく、呼び出しの回数と文脈の長さだろう。依頼文だけで2本合わせて約7万字あり、それが毎回の呼び出しに乗る
2. 変異を1種ずつ、エージェントが手で「当てる → 走らせる → 結果を読む → 戻す」と進めたのが重かったはずだ
3. 依頼文が欲張りだった。実測を8項目並べ、変異の候補を70個あまり挙げ、上限を書かなかった

## ログで確かめる

[前の記事](./07_ai_research_verification_and_harness.md)で使った方法が、ここでも使えた。Claude Codeはセッションのログをローカルに保存しており、サブエージェントの分も別ファイルで残っている。各応答にはAPIが返した使用量が記録されているので、応答ごとの重複を除いて集計した。

| 項目 | 値 |
|---|---|
| APIへのリクエスト | 170回 |
| ツール呼び出し | 213回（コマンド実行138、ファイル書き込み・編集57、ファイル読み込み16、ほか2） |
| キャッシュ読み込み | 約7,210万トークン |
| キャッシュ書き込み | 約618万トークン |
| 文脈の長さ | 開始から約90秒で約18万トークン、終了時は約72万トークン |

出力トークンはログ上では約1.3万と記録されていたが、エージェントが書いたファイルだけで約28万字あるため、この値は実態を表していない。以下では入力側（キャッシュの読み書き）だけを扱う。

なお、監査が動いていた間のメインセッション側のリクエストは5回だけだった。140%の中身は、ほぼこのサブエージェント1本の消費である。

### 推測1: 回数と文脈の長さ —— 当たっていたが、中身が違った

170回のリクエストが、平均して40万トークンを超える文脈を毎回読み込んでいた。回数と文脈の長さの掛け算で消費が決まる、という見立ては正しかった。

ただし、文脈を膨らませていたのは依頼文ではなかった。依頼文は最終的な文脈の1割程度（字数からの概算）にすぎない。残りは、コマンドの出力、読んだファイル、そしてエージェント自身が書いたスクリプトや報告書が積み上がったものだった。

### 推測2: 変異を手で1つずつ回した —— 外れ

ログのコマンドを追うと、エージェントは変異の適用・テストの実行・結果の集計・復元をスクリプトにまとめ、バックグラウンドで一括実行していた。1種ずつ手で進めていたのではない。「もっと機械的にできたはず」という反省は的外れで、機械化はすでにされていた。

### 推測3: 依頼文が欲張りだった —— 当たっていたが、効き方が違った

上限を書かなかったのは事実である。ただし、その結果は「手数が増えた」ではなかった。「待ち時間が延び、その間ずっと大きな文脈を抱えていた」という形で効いていた。これが次の節の話につながる。

## 主因: 待っている間にキャッシュが切れていた

Claude Codeは、毎回のリクエストで文脈の全体を送り直す。その大半はプロンプトキャッシュから読み込まれ、API定価では通常の入力の0.1倍で済む。一方、キャッシュへの書き込みは、5分間保持する場合で1.25倍、1時間保持する場合で2倍かかる。

「Claude Codeのキャッシュは60分持続する」と聞いていたので、ログで確かめた。使用量の記録には、書き込みがどちらの保持時間だったかが分かれて残っている。

| | リクエスト数 | 5分キャッシュへの書き込み | 1時間キャッシュへの書き込み |
|---|---|---|---|
| メインセッション | 890 | 0 | 約402万トークン |
| 監査のサブエージェント | 170 | 約618万トークン | 0 |

メインセッションは1時間、サブエージェントは5分だった。

後から公式ドキュメントを確認すると、この違いは仕様として書かれていた（[How Claude Code uses prompt caching](https://code.claude.com/docs/en/prompt-caching)）。サブスクリプションの枠内では、メインの会話は1時間、サブエージェントなどそれ以外のリクエストは、自分で設定しない限り5分になる。「60分持続する」という理解は、メインの会話についてだけ正しかったことになる。

エージェントは、変異テストのバッチが終わるのを、最長約10分の待機コマンドで待っていた。5分を超える待ちのたびにキャッシュが失効し、次のリクエストでは読み込みが0になり、文脈の全体が書き直されていた。

- 失効は9回起きた
- 書き直された文脈は1回あたり54万〜67万トークンで、合計約549万トークン
- これはキャッシュ書き込み全体の89%にあたる

API定価の倍率で重み付けすると、この9回だけで入力側の約46%を占める。同じ作業が1時間キャッシュの上で動いていれば失効は起きず、同じ倍率での試算では入力側が約4割減る。

「スクリプトに任せて、終わるまで待つ」は、一見もっとも安い動きに見える。実際には、文脈が大きくなった状態では、それがもっとも高くついていた。失効の9回は、すべて文脈が50万トークンを超えてから起きている。

## 歯止めが外れた理由: 「10分かかる」は測っていない数字だった

依頼文には、回数を抑えるための記述が1つだけあった。「テストの全実行は1回10分弱かかるので、変異は束ねて回数を抑えること」というものである。

ところが監査結果には、「この機械では全実行は約75秒だった。そのため、変異は1つずつ全実行で当てた」と書かれていた。あらためて自分で計測すると、76秒だった。10分弱という数字は、測ったことのない思い込みだった。

- 歯止めの理由は「時間がかかるから」だった
- 実際には時間がかからなかったので、エージェントは束ねる理由がないと判断した
- 76秒 × 105種で、変異テストだけで2時間強になる。全体の所要時間とおおむね合う

エージェントの判断は、与えられた条件のもとでは筋が通っている。問題は依頼の側にあった。時間を理由にした歯止めは、前提の数字が違えば外れる。そして、時間が安いこととトークンが安いことは別である。1回76秒のテストは時間としては安いが、50万トークンを超える文脈を抱えたまま100回以上待てば高くつく。

## 過剰な監査だったのか

個人開発の規模に対して過剰だったのではないか、という疑問は残る。成果とコストを並べてみる。

| 実測 | 規模 | 主な成果 |
|---|---|---|
| 掃引 | 約1万2千プレイ | 例外0・再現性の不一致0 |
| 変異テスト | 105種 | 90種を既存のテストが検出、15種が生存 |
| ロード処理の中にわざと例外を置く実験 | 変異1つ | 想定外の例外が記録を残さず「壊れたセーブ」として扱われる問題（マージ前に修正が必要と判定） |
| セーブ先への同時書き込みの実験 | 数百回 | 条件が重なると古いセーブが残る（100回中18〜66回） |

修正が必要と判定された2件のうち、1件は変異1つの小さな実験で見つかった。もう1件（終了済みのプレイに対してテスト用の進行処理が止まらなくなる）は、変異がテスト全体を停止させたことで偶然見つかった副産物である。静的な監査を担当したGemini系の2本は、どちらもマージ可と判定していた。

一方、消費の大半を占めた掃引と変異テストの主な成果は、「問題がなかったことの確認」と「どの種類の誤りを既存のテストが検出できないかの地図」だった。

これを無駄と見るかは、ゲームの性質による。Project_Orbitalは、同じシードなら同じ結果になること（決定論）と、セーブ・ロードの前後で状態が一致することを設計の柱にしている。この種の誤りはコードを読むだけでは見つけにくく、実際に走らせるしかない。「問題がなかった」という結果にも価値はある。

ただ、同じ確認を、もっと安く行う方法はあった。掃引・変異・セーブ先の実験を別々のセッションに分けていれば、それぞれが小さい文脈のまま走り、待ち時間のコストも小さく済んだはずである。必要だったのは監査の内容であって、1本にまとめて走らせることではなかった。

## 得られた教訓

- **コストは「リクエスト回数 × 文脈の長さ」で決まる。** 考える深さの設定より、文脈をどこまで育てるかのほうが効く
- **長い待ちは、文脈が小さいうちに済ませる。** キャッシュの保持時間を超える待ちは、文脈の全体を書き直させる。待ちを含む作業は、結果を短い間隔で確認するか、別のセッションに分ける
- **サブエージェントは、メインセッションと条件が違うことがある。** 今回はキャッシュの保持時間が違った。文脈を切り離せる利点と引き換えに、長時間の作業では不利になる場合がある
- **待ちの長いサブエージェントには、1時間キャッシュを設定できる。** 公式ドキュメントによれば、設定（`subagentPromptCacheTtl`）またはサブエージェント定義ごとの指定で保持時間を選べる。ただし1時間キャッシュは書き込みの単価が高いので、5分以上待たない短い作業では逆に高くつく。待ちを含む監査用のエージェントに絞って使うのが妥当だろう
- **上限は、時間ではなく回数で書く。** テストの実行回数、変異の数、ツール呼び出しの目安を依頼文に明記し、「上限に達したら、できなかった項目を未実行と書いて終える」と指示する
- **依頼文に書く数字は測る。** 「10分かかる」のような前提は、歯止めの根拠になっているほど確かめる価値がある
- **推測は実ログで確かめる。** 今回は3つの推測のうち1つが外れ、主因は推測の中になかった。推測のまま対策していれば、すでに機械化されている部分をさらに機械化しようとしていた

運用には、すでに次の規則を入れている。規模の大きい監査は、起動する前に見積もり（テストの実行回数、変異の数、掃引の規模、前回の実績との比）を出し、分けて走らせるかを決める。今回の結果を受けて、見積もりの項目に「待ちの回数と、その時点の文脈の長さ」を加える予定である。

## 残っている課題

- サブエージェントの保持時間を1時間に設定した場合に、実際にログ上で1時間キャッシュになるか、消費がどれだけ変わるかは、まだ確かめていない。次の監査で設定を変え、同じ方法でログを集計する
- 利用枠の消費がAPI定価と同じ比率で数えられているかは分からない。本記事の割合は、API定価の倍率で重み付けした場合の試算である
- 過去の監査について、同じ集計はまだ行っていない。規模と消費の関係を並べれば、見積もりの精度を上げられる
- 分割して走らせた場合に実際にどれだけ減るかは、次の監査で計測する
